## 2. הזרימה אחרי U1

1. **הוספה:** במסך המשתמשים מזינים שם, מייל ותפקיד (טכנאי / חשבונאית / אדמין; "בעלים" רק אם המוסיף הוא הבעלים). המשתמש נוצר **מאושר**, עם התיבות של התפקיד. אחר כך בוחרים אחד משניים:
   - **"שלח הזמנה במייל":** מייל בעברית מ-`noreply@bi-zi.co.il`.
   - **"צור קישור להעתקה":** קישור הזמנה חד-פעמי שמוצג פעם אחת במסך, לשליחה בוואטסאפ. בלי מייל ובלי סיסמה זמנית.
2. **הקישור (מהמייל או מוואטסאפ)** מוביל ל-**`/auth/confirm?token_hash=…&type=invite&next=/welcome`**: דף עם כפתור "המשך". רק הלחיצה (POST) מריצה `verifyOtp` בשרת, כך שסורק קישורים שפותח את הכתובת לא שורף את הטוקן. זה עובד בכל דפדפן, בלי PKCE.
3. **`/welcome`:** קביעת סיסמה (מינימום 8), ומשם ישר למערכת.
4. **שכחתי סיסמה:** אותו `/auth/confirm` עם `type=recovery`, ואחר כך `/welcome`. גם כאן אפשר "צור קישור להעתקה" מהמסך, למשתמש קיים.
5. **בכותרת:** השם פותח תפריט עם "החלפת סיסמה" (נוכחית, חדשה, אימות) ו"יציאה".
6. **הרשאות:** התפקיד מוצג בכרטיס, והתיבות נקבעות לפיו. תיבה ששונתה ידנית מסומנת "מותאם". רק הבעלים עורך מנהלים, אדמינים ואת עצמו כבעלים, והאכיפה במסד ולא רק במסך.
7. **השבתה:** "השבת" מבטל את האישור וחוסם את החשבון ב-Auth (`ban_duration`), ונכתב אירוע. "הפעל מחדש" מחזיר אותו. "מחק" מופיע רק למשתמש בלי היסטוריה.

## 3. השלבים. קודם מה שחוסם ומסוכן

### U1-1 — בדיקה מבוקרת של ההזמנה (לפני התיקון)
- **מה:** סקריפט שיוצר משתמש בדיקה `u1-invite-<hex>@bizi-test.local`, ומייצר לו קישור הזמנה ב-`generateLink({ type: "invite" })`. זה אותו קישור (`ConfirmationURL`) שהמייל שולח, בלי לשלוח מייל ובלי לגעת במכסה. אחר כך הסקריפט פותח את הקישור בדפדפן אמיתי (Playwright) על האתר החי, ובודק את התוצאה: האם `/welcome` מציג "הקישור אינו תקין" או את טופס הסיסמה, ומה מופיע בכתובת (`#access_token` מול `?code`).
- **ניקוי:** ב-`finally`: מחיקה של אירועים שנוצרו, ואז של המשתמש. **מוודאים שהמחיקה הצליחה:** ‏GET אחרי המחיקה מחזיר 404, ואין שורה ב-`profiles`.
- **מיגרציה:** לא.
- **מה צריך ממך:** אישור להריץ על הייצור. נוצר משתמש אחד, ונמחק באותה ריצה.

### U1-2 — `/auth/confirm` ותבניות בעברית
- **מה:** ראוט `GET /auth/confirm` שמציג דף "המשך", ו-`POST` שמריץ `verifyOtp({ token_hash, type })` דרך הלקוח של השרת (‏cookies), ומעביר ל-`next`. מותרים רק `next` פנימיים שמתחילים ב-`/`. בכשל מוצג דף ברור עם שליחה מחדש. ‏`/auth/callback` נשאר לקישורים ישנים.
- **התבניות:** ההזמנה והאיפוס מפנים ל-`{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=invite|recovery&next=/welcome`. כותרות ותוכן בעברית, RTL. נכתבות דרך Management API (‏PATCH ל-`config/auth`), אחרי שאתה מאשר את הנוסח.
- **בדיקה:** חוזרים על הבדיקה של U1-1 אחרי התיקון, ומצפים לטופס סיסמה. משתמש בדיקה נמחק בסוף.
- **מיגרציה:** לא.
- **מה צריך ממך:** אישור נוסח התבניות, ואישור לעדכן אותן בהגדרות Auth.

### U1-3 — סגירת ההרשמה ו-8 תווים
- **מה:** ‏`disable_signup = true`, ‏`password_min_length = 8`, דרך Management API.
- **בדיקה חיה אחרי השינוי:**
  - ‏Admin invite / `generateLink` / `createUser` עובדים (משתמש בדיקה, ונמחק).
  - ‏`signUp` ציבורי עם מפתח anon נדחה.

  - ‏`/join` עובד (בדיקת עשן של העמוד, בלי לשלוח הרשמה).
- **חזרה אחורה:** אם משהו נשבר, מחזירים את הערך הקודם באותה קריאה.
- **מיגרציה:** לא.

### U1-4 — הגנה על הבעלים והפרדת "אדמין" מ"בעלים"
- **מה, במסד (מיגרציה 0119):** טריגר `BEFORE UPDATE` על `profiles`: רק משתמש עם `role='owner'` רשאי (א) לשנות שורה של משתמש שהוא `owner`, אדמין (`role='admin'`) או `can_manage_users`, (ב) להעניק `can_manage_users`, ו-(ג) לקבוע `role` כ-`owner` או `admin`. אותו כלל ל-DELETE. כש-`auth.uid()` ריק (‏SQL Editor או service role), אין הגבלה, כמו ב-`guard_studio_admin_flag`.
- **התפקיד "אדמין":** ערך חדש `role='admin'` עם כל התיבות. **נבדק 19.10:** קיים `profiles_role_check` שמתיר רק `owner` / `tech` / `bookkeeper`, ולכן 0119 מרחיבה אותו ל-`admin`. מסכי הבעלים נשארים מוגבלים ל-`role='owner'` (הבדיקות הקיימות `role !== "owner"`), ולכן אדמין לא רואה אותם.
- **בקוד:** הפריסט "אדמין" קובע `admin` ולא `owner`. "בעלים" מוצג רק לבעלים.
- **מיגרציה:** כן (0119). כרגיל: dryrun ו-verify על Postgres מקומי, אחר כך אתה מחיל ומריץ gen types.
- **מה צריך ממך:** החלת 0119, gen types, והכרעה מה עושים עם `shiri.ab@gmail.com` (היום `owner` עם ניהול משתמשים): נשארת בעלים או עוברת לאדמין? וגם `eli@bi-zi.co.il` (`owner`).

### U1-5 — SMTP דרך Resend (B31)
- **מה צריך ממך, לפי לוח:**
  1. **Resend:** פתיחת חשבון, הוספת הדומיין `bi-zi.co.il` (אזור EU), ויצירת API key עם הרשאת **Sending access** בלבד.
  2. **Cloudflare:** להוסיף את הרשומות ש-Resend מציג (DKIM ב-`resend._domainkey`, ‏MX ו-SPF על תת-הדומיין להחזרות), כ-**DNS only** (ענן אפור). את ה-SPF הראשי לא נוגעים. מחכים ל-Verified ב-Resend.
  3. **Supabase** (‏Authentication › Emails › SMTP Settings): Enable Custom SMTP, ‏host `smtp.resend.com`, ‏port 465, ‏user `resend`, ‏password = ה-API key (מוזן ישר בלוח, לא בצ'אט ולא בקובץ), sender `noreply@bi-zi.co.il`, ‏name "Bizi Podclub". ואחר כך ב-Rate Limits להעלות את "emails per hour" ל-30.
- **מה אני עושה:** קריאה בלבד של ההגדרות כדי לוודא שהן נקלטו. אחר כך בקשת איפוס לכתובת שלך, ובדיקה ש-`dkim=pass` ו-`dmarc=pass` בכותרות המייל.
- **מיגרציה:** לא. **קוד:** לא.

### U1-6 — מסך המשתמשים: הוספה עם תפקיד, וקישור להעתקה
- **מה:**
  - ‏`POST /api/users` מקבל `role`. המשתמש נוצר (‏`createUser`, ‏`email_confirm: true`, בלי סיסמה), ומיד מאושר עם התיבות של התפקיד.
  - שתי פעולות: "שלח הזמנה במייל" ו"צור קישור להעתקה".
  - הקישור נוצר ב-`generateLink`, ובונים ממנו כתובת `/auth/confirm` מה-`hashed_token`. הוא מוצג פעם אחת במודאל עם כפתור העתקה, ולא נשמר, לא נרשם בלוג ולא נכנס לאירוע. באירוע נרשם רק שנוצר קישור.
  - גם למשתמש קיים: "קישור כניסה חדש" (סוג recovery).
  - "הוסף ידנית" והסיסמה האקראית נמחקים.
  - בכרטיס: תווית התפקיד ו"מותאם". הכפתורים לעריכת מנהלים מוסתרים למי שאינו בעלים (האכיפה עצמה ב-U1-4).
