# E17 — דף הרשמת לקוח + כניסה מהבוט

**שלב: E17-1 — סקירה ואפיון בלבד. נכתב 11.10.2026.** אין כאן מיגרציה ואין שינוי קוד. כל מה שמסומן "הצעה" ממתין להכרעה. כל נוסח שמסומן "טיוטה — לאישור בעלים" לא נשלח לאף אחד.

**יחס ל-E5:** E5 ("טופס פתיחת לקוח לשליחה ללקוחות") הוא שלד מ-16.8 לאותו אפיק בדיוק: קישור ציבורי עם טוקן, ונוצרת רשומה שממתינה לאישור. E17 הוא האפיון המלא שלו. **הצעה:** לסגור את E5 כ"מוזג ל-E17" ברגע ש-E17-2 נפתח.

## הכרעות שכבר נקבעו

- הרשמה יוצרת לקוח במערכת בסטטוס "ממתין לאישור"; הלקוח לא נכנס למורנינג עד אישור אדמין. — הכרעת בעלים 11.10
- נרשם חדש מקפיץ פופ-אפ לבעלי הרשאה (מסך הלקוחות ו/או מסך אישורי המסמכים) + הודעת בוט לבניה ולאלי. — הכרעת בעלים 11.10
- לקוח קיים לא יכול לפתוח כפילות דרך ההרשמה. — הכרעת בעלים 11.10
- בהרשמה הלקוח מזין מספר אחד או שניים שיורשו להזמין הקלטות לפודקאסט. אחרי השליחה הלקוח לא יכול לשנות אותם — רק אדמין. — הכרעת בעלים 11.10
- ההזמנה הראשונה של לקוח שנרשם דרך הדף דורשת אישור של בניה או אלי, והבוט מתריע עליה. מההזמנה המאושרת הראשונה ואילך — כמו כל פודקאסט. פודקאסטים קיימים לא מושפעים. — הכרעת בעלים 11.10
- מספר לא משויך שפונה לבוט מקבל בהודעה הראשונה אפשרות "פתיחת לקוח חדש" עם קישור לדף ההרשמה (מחליף את התשובה הניטרלית). — הכרעת בעלים 11.10
- תיבת אישור תנאי פרטיות עם קישור ל-/privacy. — הכרעת בעלים 11.10
- הקישור שהבוט שולח נושא את מספר הפונה ממולא ונעול (מאומת כי פנה ממנו); הדף הכללי שנשלח ידנית מקבל הגנת ספאם בסיסית. — המלצת Claude, טרם אושרה

### 1. כרטיס לקוח

**הטבלה `clients`** ([database.types.ts:576-590](../../src/lib/supabase/database.types.ts#L576-L590)):

| עמודה | חובה? | מקור |
|---|---|---|
| `name` | **חובה** (NOT NULL, בלי ברירת מחדל) | 0001 |
| `normalized_name` | **חובה**, **ייחודי** (`clients_normalized_name_idx`) — זו **הייחודיות היחידה** בטבלה | 0001 |
| `billing_mode` | NOT NULL, ברירת מחדל `per_episode`. enum: `per_episode / retainer / package / none` | 0002 |
| `payment_terms` | NOT NULL, ברירת מחדל `immediate`. enum: `immediate / net_30 / net_60 / eom_30 / eom_60 / eom_90` | 0002 |
| `billing_cadence` | NOT NULL, ברירת מחדל `per_episode`. enum: `per_episode / monthly / every_n`. ה-CHECK מחייב את `billing_every_n` כשהערך הוא `every_n` | 0047 |

  - מיילים מרובים הם `emails: string[]` במורנינג. כל כתיבה מחליפה את כל הרשימה.
  - טלפון הוא שדה אחד.
  - לח.פ יש בדיקה של 9 ספרות (`validateTaxId`, [taxId.ts](../../src/lib/clients/taxId.ts)), בשרת ובקליינט.
- **איפה נאכפת החובה:**
  - במסד: רק `name` / `normalized_name`. יש גם טריגר `guard_client_money_columns` (0010): שינוי של `default_rate` / `payment_terms` / `billing_mode` מחייב `can_edit_money`.
  - ב-API: `POST /api/clients` ו-`POST /api/morning/clients/create` דורשים רק `name`.
  - אין zod באף מקום. כל האימות כתוב ביד בראוטים.
- **RLS:**
  - `clients_view` = `can_view_money()` (0021)
  - `clients_insert` = `can_edit_money() or can_import()` (0002)
  - `clients_update` = `can_edit_money()` (0002)
  - אין policy ל-DELETE.

### 2. פתיחת לקוח במורנינג

- **הקריאה:** `createMorningClient` ([morning/client.ts:504-521](../../src/lib/morning/client.ts#L504-L521)) שולחת `POST /clients` עם `name`, ובנוסף `taxId` / `phone` / `emails` / `address` רק כשהם קיימים. הכתובת נשלחת כמחרוזת אחת. לא נשלחים `country` / `city` / `paymentTerms`.
- **הקורא היחיד:** `POST /api/morning/clients/create`.
  - הרשאה: `can_edit_money`.
  - מהבקשה מגיע מייל **אחד** (`emails: [email]`).
  - הזרימה בשני שלבים: `confirm=false` מדווח כפילויות ולא יוצר כלום, `confirm=true` יוצר.
- **אילו שדות מורנינג מחייב:** **לא מתועד בריפו.** הקוד אוכף רק `name`. לפני E17-5 צריך לברר את זה בתיעוד של Morning, בלי קריאה חיה.
- **המזהה אצלנו:**
  - `clients.morning_client_id`. **לא ייחודי** מאז 0026, כי כמה לקוחות שלנו יכולים לחלוק לקוח מורנינג אחד.
  - טבלת כינויים `client_morning_ids` (0094) עם טריגר סנכרון.
  - שער ההנפקה הוא `if (!client.morning_client_id)` ב-[enqueue.ts:302](../../src/lib/documents/enqueue.ts#L302). **לקוח ממתין שאין לו מזהה מורנינג ממילא לא יכול לקבל מסמך.** זה עוזר לנו.
- **dry-run:**
  - `isDryRun()` = `MORNING_DRY_RUN !== "false"`, כלומר דלוק כברירת מחדל ([client.ts:35-37](../../src/lib/morning/client.ts#L35-L37)). במצב הזה `createMorningClient` מחזירה `dry-client-<uuid>` בלי קריאה לרשת.
  - 🔴 **מלכודת:** הראוט כותב את המזהה המדומה הזה ל-`clients.morning_client_id` ([create/route.ts:129](../../src/app/api/morning/clients/create/route.ts#L129)). מסלול E17 **אסור לו** לרשת את ההתנהגות הזאת.
  - **קריאות** ממורנינג (`listClients` וכו') יוצאות חיות גם במצב dry-run.
- **תורי אישור:**
  - `approval_requests` משמש לפעולות הרסניות בלבד.
  - `pending_documents` משמש למסמכים בלבד.
  - **יצירת לקוח לא עוברת באף אחד מהתורים.**

- ללקוח אין שום נתיב לערוך את הטבלה. "נעילת המספרים" אחרי השליחה קיימת כבר היום.

### 5. אישור אוטומטי ומסלול "ממתין לאישור ידני"

- **המתג:** `BOOKING_AUTO_APPROVE === "true"`, כבוי כברירת מחדל ([decide.ts:104-106](../../src/lib/booking/decide.ts#L104-L106)).
- **ההכרעה:** פונקציה טהורה, `autoApproveVerdict` ([decide.ts:171-178](../../src/lib/booking/decide.ts#L171-L178)):
  ```ts
  if (!input.switchOn) return { auto: false, reason: "switch-off" };
  if (input.approvedSameDay >= 1) return { auto: false, reason: "second-same-day" };
  return { auto: true };
  ```
- **מסלול הממתין כבר קיים:**
  - הבקשה נשארת `pending`, ונשלחת `bizi_booking_pending` עם `{{5}}` = סיבה. התבנית הולכת **לכל** `WHATSAPP_NOTIFY_NUMBERS`, כלומר לבניה ולאלי.
  - הלקוח מקבל בבוט את `OUTCOME.pending` ([flow/copy.ts:171-173](../../src/lib/whatsapp/flow/copy.ts#L171-L173)):
    > `קיבלנו! 🙌 הבקשה ל${showName} ליום ${dow} ${d.m} ב-${start} נשלחה לאולפן ותאושר בהקדם.`
  - תוויות הסיבה מוגדרות ב-`PENDING_REASON_LABEL` ([notify.ts:171-177](../../src/lib/whatsapp/notify.ts#L171-L177)).
  - **סיבה חדשה כמו "הזמנה ראשונה של לקוח חדש" היא רק ערך נוסף ב-`{{5}}`, ולא דורשת תבנית חדשה.**
- **אישור ידני:**
  - נעשה במסך `/bookings`, דרך `POST /api/bookings/[id]/approve`. הראוט פתוח **לבעלים בלבד** (`role==='owner'`).
  - אישור ידני **לא שולח ללקוח שום הודעה**. המסך מציע רק קישור wa.me.
- **סטטוסים:** `pending / approved / declined / cancelled`.

### 7. פודקאסט חדש (`shows`)

- **שדה החובה היחיד בלי ברירת מחדל:** `name`.
- **שדות שהאדמין ישלים באישור:**

| עמודה | הערה |
|---|---|
| `client_id` | nullable. בלי `client_id` הראוט כופה `billing_mode='none'` ומבקש אישור "פנימי" |
| `billing_mode` | **enum נפרד מזה של הלקוח**: `per_episode / contract / none`. ברירת מחדל במסד `per_episode`; ב-`POST /api/shows` ברירת המחדל `none` |
| `pricing_model` | `per_episode / per_hour`, ועמו `default_rate` **או** `hourly_rate`. ה-CHECK `shows_one_rate_per_model` מתיר תעריף אחד בלבד |
| `default_studio` | טקסט חופשי בלי FK. השמות הקנוניים מגיעים מ-[studios.ts](../../src/lib/calendar/studios.ts) |
| `aliases` | 🔴 **קריטי לזרימה:** בלי כינוי נקי `ensureBookingLink` מחזיר `no-clean-alias` והבוט לא נותן קישור. סנכרון היומן מזהה הקלטה לפי כינוי |
| `has_episode`, `reels_count`, `camera_count` | יש להם ברירות מחדל |

- **מי ממלא היום:** רק `POST /api/shows` (הרשאה `can_edit_stages` או `can_edit_money`; שדות הכסף רק עם `can_edit_money`), מתוך `NewShowModal` ([ShowsClient.tsx:1535-1640](../../src/app/shows/ShowsClient.tsx#L1535-L1640)).
- טריגר `guard_show_money_columns` דורש `can_edit_money` כדי לשנות `default_rate`, `client_id` או `billing_mode`.

### 8. פופ-אפ לאדמינים

**אין היום מנגנון פופ-אפ, פעמון, toast או realtime.** יש שלושה מנגנונים, כולם מחושבים בשרת בטעינת הדף:
- (א) **כרטיס מונה בדף הבית.** הרישום ב-[modules/registry.ts](../../src/modules/registry.ts). התקדים: `bookingsModule` ("בקשות ממתינות", tone `warn`, בעלים בלבד). ⚠️ `getMetric` רץ עם ה-session client, ולכן טבלה שסגורה ל-session צריכה admin client.
- (ב) **התראה ב-`/radar`** ([alerts.ts](../../src/modules/radar/alerts.ts)). מוצגת רק ל-`can_view_money`.
- (ג) **באנר בתוך מסך.** קיים ב-`/documents` כבאנר "ממתינים מעל 24/72 שעות" ([DocumentsClient.tsx:1241-1250](../../src/app/documents/DocumentsClient.tsx#L1241-L1250)). ב-`/clients` אין באנר.

**הצעה:** כרטיס מונה בדף הבית, ובנוסף דיאלוג שנפתח בטעינת `/clients` כשיש הרשמות ממתינות, עם כפתור "לטיפול" ו"אחר כך" (הסגירה נזכרת ב-sessionStorage לאותה הרשמה). אין צורך ב-realtime: את ההתראה המיידית נותנת הודעת הבוט לבניה ולאלי. אם רוצים אותו גם ב-`/documents`, זה אותו רכיב ואותה שאילתה.

**מסלול דחייה:**
- האדמין לוחץ "דחייה" ויכול להוסיף סיבה פנימית.
- הלקוח עובר ל-`rejected` ונשאר כרשומה, לא נמחק. ראו שאלה 7 לגבי מחיקה בפועל ופרטיות.
- הטוקן נשרף.
- לא נוצר כלום במורנינג.
- האם הלקוח מקבל הודעה: שאלה 6.

**הדף הכללי (`/join` בלי טוקן):**
- נשלח ידנית.
- המספרים לא ממולאים ולא מאומתים, ומסומנים `verified=false` ברשומת ההרשמה.
- האדמין רואה את הסימון לפני האישור.
- הגנת ספאם בסיסית, ראו "סכמה" למטה.

### כפילות — מה רואים

**הצעה לבדיקה בשליחה, לפי הסדר:**
1. **מספר:** כל אחד מהמספרים כבר קיים ב-`booking_contacts`. מספר שמגיע מהבוט לא יכול להיות שם, אחרת הבוט לא היה מציע הרשמה. לכן הבדיקה רלוונטית לדף הכללי ולמספר השני.
2. **ח.פ:** התאמה מדויקת ללקוח מקומי, לפי הצעת העמודה בחלק הסכמה, ולהרשמה ממתינה אחרת.
3. **שם:** `normalized_name` מדויק. האינדקס הייחודי ממילא יפיל insert כזה.
4. **שם דומה (levenshtein):** **לא חוסם.** רק מסומן לאדמין.

- **הלקוח רואה** (טיוטה — לאישור בעלים):
  > נראה שכבר יש לנו כרטיס עבורכם 🙂 העברנו את הפרטים לצוות, ונחזור אליכם כדי לחבר את המספר לפודקאסט.
  - הנוסח זהה לכל סוג התאמה, ולא מגלה **מה** הותאם ולא את שם הלקוח הקיים. כך הדף לא יכול לשמש לבירור "האם עסק X לקוח של ביזי".
- **בניה ואלי מקבלים** את אותה תבנית הרשמה (למטה), עם `{{4}}` = "התאמה לכרטיס קיים: <שם> (לפי <שדה>)".
- **הצעה:** לשמור גם הרשמת-כפילות כרשומה בסטטוס `duplicate` עם `duplicate_of_client_id`, כדי שהאדמין יוכל לשייך את המספר ללקוח הקיים בלחיצה.

### שינויי סכמה מוצעים (בלי מיגרציה — לאפיון בלבד)

**1. `clients.status`** — `text NOT NULL default 'active'` עם CHECK על `('pending','active','rejected')`.
- כל השורות הקיימות נכנסות כ-`active`.
- ⚠️ **רדיוס הפגיעה:** כל קורא שמציג רשימת לקוחות צריך לסנן `status='active'`:
  - `ClientCombobox`
  - `/clients`
  - `/projects`
  - ההנפקה. כאן כבר מוגן, כי אין `morning_client_id`.
  - הייבוא
  - החיפוש הגלובלי
- **המיפוי של הקוראים הוא חלק מ-E17-2.**
- RLS: בלי שינוי ב-policy. לקוח ממתין נראה רק למי שרואה לקוחות היום (`can_view_money`).

**2. `client_registrations`** — הפרטים שהלקוח מסר ואין להם עמודה בלקוח:
- `id`, `client_id → clients` (nullable כשזו כפילות), `status` (`pending / approved / rejected / duplicate`), `duplicate_of_client_id`
- `source` (`bot / web`), `link_id → registration_links`
- `legal_name`, `tax_id` (9 ספרות), `contact_name`, `emails text[]` (לפחות 1), `phone`, `address`
- `podcast_name`
- `booking_numbers jsonb`: `[{name, wa_id, verified}]`, באורך 1-2
- `privacy_accepted_at`, `privacy_version`: ערך `PRIVACY_UPDATED_AT` ברגע השליחה
- `decided_by`, `decided_at`, `reject_reason`, `created_at`
- **RLS:** כמו `booking_contacts` (0103): דלוק בלי policies, `revoke all` מכל תפקידי ה-session, ו-canary. הגישה רק דרך ראוטים עם שער ו-service role. כרטיס המונה בדף הבית ישתמש ב-admin client, כמו `/radar`.

**3. `registration_links`** — טוקן הקישור:
- `token`: 32 בתים base64url, כמו `booking_links`. **העמודה מוחרגת מכל grant של session**, כמו ב-0096.
- `wa_id`: מלא כשהקישור יוצא מהבוט, null כשנוצר ידנית.
- `created_by` (null = בוט), `expires_at` (הצעה: 7 ימים), `used_at` (חד-פעמי), `revoked_at`.
- **הצעה:** קישור פעיל אחד לכל `wa_id`. כשאותו מספר כותב שוב, הבוט מחזיר את אותו קישור.
- המספר **לא** מופיע ב-URL. השרת פותר אותו מהטוקן.
- ה"אימות" אמיתי: ה-`wa_id` הגיע ב-webhook חתום HMAC של Meta.

**4. `shows.first_booking_needs_approval`** — `boolean NOT NULL default false`.
- כל הפודקאסטים הקיימים מקבלים `false`, ולכן לא מושפעים, כמו שהוכרע.
- האישור של E17 קובע `true`.
- `autoApproveVerdict` מקבל קלט נוסף, ובודק אותו **לפני** `second-same-day`:
  ```ts
  if (input.firstBookingNeedsApproval) return { auto: false, reason: "first-booking" };
  ```
- `PendingReason` מקבל `"first-booking"` עם התווית `"הזמנה ראשונה של לקוח חדש"`.
- הדגל יורד ב-`approveBookingRequest` כשהאישור מצליח, באותו עדכון. ביטול או דחייה של ההזמנה הראשונה **לא** מורידים אותו.
- שינוי הדגל ידנית מחייב `can_edit_money`, כהרחבה של `guard_show_money_columns`.

**5. `booking_contacts.registration_id`** — FK nullable ל-`client_registrations`, לתיעוד המקור. לא נדרש שינוי RLS.

**6. (תלוי בשאלה 1) `clients.tax_id`** — `text` עם CHECK על 9 ספרות, ואינדקס ייחודי חלקי (`where tax_id is not null`). תהיה גם השלמה חד-פעמית ממורנינג (סקריפט שהבעלים מריץ, לא אני).

**הגנת ספאם לדף הכללי (בלי שירות חיצוני):**
- honeypot.
- זמן מילוי מינימלי (פחות מ-3 שניות = נדחה בשקט).
- תקרה של הרשמות ממתינות מהדף הכללי בכל המערכת (הצעה: 10). מעבר לה הדף מציג "נסו שוב מאוחר יותר" והבעלים מקבל הודעה.
- מגבלות אורך כמו ב-[request.ts](../../src/lib/booking/request.ts) (`GUEST_MAX_CHARS` / `NOTE_MAX_CHARS`).
- `robots: noindex` ו-`referrer: no-referrer`, כמו ב-`/b/[token]`.
- הדף נכנס לרשימת ההיתר ב-[middleware.ts](../../src/lib/supabase/middleware.ts): `/join`, `/api/join/`.
- כל כישלון טוקן מחזיר מסך אחיד אחד, כמו `DeadLink`.

**/privacy:** הטופס אוסף ח.פ, מיילים, טלפון וכתובת. לכן צריך סעיף חדש ב-`data` בתוך [privacy.ts](../../src/lib/legal/privacy.ts) והעלאת `PRIVACY_UPDATED_AT`. העוגן `#deletion` לא משתנה, כי Meta שומר אותו.

## שאלות פתוחות

1. **בדיקת כפילות לפי ח.פ — מול מה?** ח.פ של לקוחות קיימים נמצא רק במורנינג. האפשרויות:
   - (א) קריאה חיה למורנינג מכל שליחה ציבורית. הקריאה היא `listClients`, סריקה של עד 50 עמודים, כך שכל אחד מהאינטרנט מפעיל קריאות למורנינג.
   - (ב) עמודת `clients.tax_id` עם השלמה חד-פעמית ממורנינג.
   - (ג) בדיקה מול מורנינג רק בזמן האישור, כשהאדמין מחובר. אז "לא ניתן לפתוח כפילות" נאכף באישור ולא בשליחה.
   - **הצעה:** (ב) בשליחה, ובנוסף (ג) באישור כרשת ביטחון.
2. **שם זהה לשם של לקוח קיים**, כשאלה שני עסקים שונים: האינדקס הייחודי על `normalized_name` חוסם. האם להתייחס לזה ככפילות, או לאפשר לאדמין לשנות שם באישור?
3. **לקוח קיים שכותב ממספר חדש** (למשל מפיק חדש): נוסח 1 מציע לו "פתיחת לקוח חדש". האם להוסיף כפתור שני, "אני כבר לקוח", שמתריע לבעלים במקום לפתוח טופס?
4. **הדף הכללי:** מספרים שהוזנו שם לא מאומתים. האם אישור האדמין מספיק כאימות, או שצריך שהמספר יכתוב לבוט לפני שהוא מורשה?
5. **שדות הטופס:** מה חובה ומה רשות? **הצעה:** חובה — שם עסק, ח.פ/ע.מ, איש קשר, מייל אחד לפחות (עד 3), טלפון, שם הפודקאסט, ומספר מורשה אחד לפחות עם שם. רשות — כתובת ומספר שני. בנוסף: אילו שדות מורנינג מחייב ב-`POST /clients`? הריפו לא מתעד את זה.
6. **דחייה:** האם הלקוח מקבל הודעה (תבנית `bizi_client_rejected`) או שהבעלים פונה אליו ידנית?
7. **רשומה שנדחתה:** לשמור (`rejected`) או למחוק את הפרטים האישיים אחרי X ימים? זה נוגע לסעיף השמירה ב-/privacy.
8. **מי רואה את הפופ-אפ ומי מאשר:** רק בניה ואלי, או כל מי שיש לו `can_edit_money` (כולל שירי)? היום אישור הזמנות פתוח ל-`role='owner'`, והכרטיסייה "הרשאות הזמנת חדרים" פתוחה לדגלי הכסף.
9. **הרשמה אחת = פודקאסט אחד?** או שלקוח יכול לרשום כמה פודקאסטים באותו טופס?
10. **תוקף הקישור:** 7 ימים, חד-פעמי? ומה קורה כשהלקוח פותח שוב קישור שכבר שימש: מסך "כבר שלחתם" או מסך אחיד?
